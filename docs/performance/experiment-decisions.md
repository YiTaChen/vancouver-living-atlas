日期：2026-09-06。基準：`7443b95`；保留實作：`a8b48d4`，分支 `perf/progressive-city-startup`。

**後續發布更新（2026-09-06）：** 使用者其後明確要求部署新增語言版本，已將 `fa83a58`（含本分支優化與十語介面）發布至 Firebase；main 仍未合併。下文「尚未部署」與決策描述保留原實驗階段的時間背景。

本紀錄補充[效能報告](progressive-startup.md)，供日後優化或合併至 main 時參考。**「採用」只代表保留在實驗分支，尚未合併 main 或部署。** 本次目標是縮短初次進入城市，同時保留全景切換至走路、開車、開船的連續體驗。

## 資料可信度與判讀方式

- 最終比較只使用已提交的 [baseline](baseline/) 與 [candidate](candidate/) Chrome 原始報告，各設定／版本三次；建置及自動測試不與量測同時執行。
- 前期 IAB 探索測試存在背景建置／測試干擾，以及反覆載入後記憶體壓力、無回應問題。舊版也受影響，不能認定這些現象由某項新實作造成。先前直接猜測 Worker 複製成本是主因，也沒有足夠剖析證據證實。
- 前期資料已另外保存為[探索摘要](experiments/exploratory-summary.json)，並保留各撤回方案的代表原始報告。即使記錄器標示 `valid: true`，也只代表其頁面前景等檢查通過，不代表整台電腦沒有競爭負載。
- 以下前期秒數用來記錄「當時看到了什麼、為什麼沒有採用」，**不能拿來與最終 Chrome 數據計算改善百分比**。
- 多項保留變更一起接受最終測試，沒有逐項開關的消融實驗。因此不能把總改善拆成各項獨立收益，亦不能加總前期局部時間差。
- 撤回的原型程式及大型產物沒有納入分支。原始報告的來源指紋可識別當時快照，不能重建已撤回原型；資產大小來自當次產物觀察，沒有保留可重新核算大小的檔案。

## 實際嘗試後撤回的方案

| 方案 | 做法與觀察結果 | 決策與原因 | 未來重新評估的條件 |
| --- | --- | --- | --- |
| 預先產生完整 3D 道路 | 將道路幾何預算成可下載資料。當次 base64 JSON 約 101 MB，gzip 約 24 MB；未完成可用的整頁速度比較。 | 撤回。額外下載／解碼／暫存負擔太大，特別不適合直接加到手機首屏。不能只計算省下的建模 CPU。 | 改為真正的緊湊二進位格式、空間分塊與快取後，再同時計算下載、解碼、GPU 上傳與峰值記憶體。 |
| 預先產生 2D 道路計畫 | 預算道路圖、路面多邊形與標線；最終貼地與碰撞仍在本機完成。JSON 約 11.25 MB，gzip 約 3.1 MB。兩次前期頁面觀察為 15.18、15.58 秒；道路階段約 2.17、2.00 秒，早期即時計算基準約 3.5–3.7 秒。 | 撤回。局部 CPU 下降，但加了約 3 MB 壓縮下載，整頁收益沒有得到可靠確認。相關產物、生成器及專用載入設定均未保留。 | 必須先用冷快取、限速網路及手機驗證「下載＋解碼＋貼地」總成本，再與即時計算比較。 |
| 一次性道路 Worker | 在背景執行同一套 2D 工廠，主執行緒建造土地／背景，最後等待結果。前期整頁 16.62 秒；等待約 2.38 秒，後續道路建造約 2.34 秒。 | 撤回。把工作移到 Worker 不等於移除工作，等待仍在進入城市前的必要路徑上；沒有可靠淨收益。 | 先分辨工廠計算、啟動、傳入、傳出、解碼各段成本，找到確實可重疊的工作。 |
| 延後等待 Worker | 把建築、橋梁與自然環境放到等待之前，增加重疊；並恢復道路子物件順序，以維持貼地與碰撞比對順序。觀察 19.01 秒、等待約 3.01 秒；該輪有其他工作干擾。 | 撤回。這一輪不能證明方案一定較慢，但也不足以支持採用；調整初始化順序額外增加依賴風險。 | 在安靜環境重新測量，且必須證明地面資料、樹木避讓、碰撞順序完全一致。 |
| Worker ready 握手 | 等背景工廠載入完成後才送工作，降低主執行緒先進入重工作造成的啟動排程不確定性。觀察 17.19 秒；握手約 26 ms，等待結果仍約 2.61 秒。 | 撤回。握手完成快，並未消除之後的等待；沒有證明啟動握手是主要瓶頸。 | 只有追蹤資料確認 Worker 啟動受阻時，才值得重試。 |
| Worker 可轉移緩衝區 | 用 JSON UTF-8 的單一 ArrayBuffer 傳回結果，取代大量巢狀陣列的直接結構化複製；保留數值精度。觀察 17.35 秒；握手約 20 ms、等待約 2.73 秒、道路階段約 1.86 秒。 | 撤回。沒有可靠改善；序列化、編碼與主執行緒解碼本身也有成本。**不能據此宣稱傳輸複製已被證實是主因。** | 真正的 typed-array 二進位資料模型可能不同，但仍需完整端到端剖析，不能只看傳輸步驟。 |

## 保留在分支的方案

| 方案 | 實作與結果 | 採用理由、代價與界限 |
| --- | --- | --- |
| 必要資料並行請求 | GeoJSON 與其他必要 JSON 一起請求，移除後段逐一等待；保留必要／可選資料的失敗行為。 | 不新增資料包、不延後移動模式準備。獨立網路收益未量測；並行請求不等於減少總下載量。 |
| 共用地形頂點計算 | 以精確座標快取相同頂點的高程與公園分類；建造完成後可回收。 | 避免同一頂點重複採樣，不降低地形解析度；增加短暫 Map 記憶體，沒有宣稱整體 RAM 因此下降。 |
| 地基查找 Map | 用每個建物鍵對應的第一個來源部件，取代反覆線性搜尋。 | 保持原本選第一個部件的語意，減少重複查找；沒有單獨計時歸因。 |
| 道路修補空間篩選 | 建立保留原始順序的範圍索引，縮小道路／步道與高度約束的候選集合。 | 精確幾何運算不變；索引本身有記憶體成本，沒有假設所有資料規模都會更快。 |
| 略過遠處道路暫存資料 | 先檢查修補區域與完整漸變邊界，再決定是否展開世界座標陣列；保留來源順序與保護標記。 | 避免為不可能參與局部修補的道路複製大量頂點。最終物理地面資料與舊版逐位元一致；未量測全程峰值記憶體差值。 |
| 屋頂裝飾背景分批建造 | 全景每幀預算 1.5 ms，運鏡／移動中 0.5 ms，每幀最多 64 步；取消時釋放尚未加入場景的物件。 | 屋頂本體仍完整；只延後小型設備。三次桌面觀察共 11,025 步，單次 pump 最高 1.2–1.4 ms、零失敗。這是合作式預算，不是硬即時保證，也不等於已量測全部 GPU 上傳成本。 |
| Balanced／相容模式不新建屋頂裝飾 | 三次相容模式啟動皆執行零步屋頂準備。High／Ultra 建好後保留。 | 效能模式不必持續準備不必要的小物件。若先用 High 建好再切 Balanced，既有物件仍保留，並不立即回收全部細節記憶體。 |

保留版本的合併結果：桌面頁面中位數 18.13 → 15.75 秒，相容設定 15.68 → 15.07 秒；建構階段主執行緒中位數約下降 3.2%／4.2%。三次樣本範圍重疊，只能視為初步本機觀察。375 項測試與正式建置通過；1,014 個地面／道路模型的屬性資料共 115,305,684 bytes，SHA-256 新舊一致，詳見主報告。

## 只評估、沒有實作的方向

- **選擇走路／開車／開船後才下載必要資源：不採用。** 使用者明確要求保留立即進入與連續運鏡，不能讓選擇模式變成等待點。
- **進入駕駛／開船後再載入內裝：允許，但本輪暫緩。** 整個 navigation 初始化約在 0.1 秒量級；沒有單獨量出 cockpit 的成本，因此不能把全部 navigation 時間當成可省下的內裝時間。先處理較大的道路／地形瓶頸。
- **載具外觀漸進細節：未實作。** 目前沒有證據顯示它是初始載入的主要瓶頸；外觀與操作資源維持立即可用。
- **預算土地或局部貼地修補、更多快取：曾考慮，但未形成完整實驗。** 不能列為已驗證有效／無效。未來需處理來源版本、幾何順序、地面一致性及失效回退。
- **新增大範圍地理分塊串流：未實作。** 本版不是整座城市的空間串流改寫；不可把屋頂分批建造描述為所有模型皆已動態載入。
- 專案原本已有 facade、Ultra 地標、樹木等細節管理機制；本次沿用，不能把既有功能計入新增成果。

## 日後優化 main 的依據與先後順序

1. **先追蹤首次駕駛長幀。** 本次首次測到最大 567 ms，預熱重測最大 18.7 ms。原因未定位，不能歸因給新屋頂佇列、特定 shader 或某一資源；需要 CPU／GC／GPU／資產時序追蹤。
2. 重測目前 main 與候選分支：若 main 已有新修改，先更新比較基準。使用同瀏覽器、同尺寸、同品質、相同快取條件，交錯多次測量；建置與其他 3D 場景不得干擾。
3. 補 iPhone／iPad 真機與限速網路測試，分別觀察首次顯示、可操作、首次模式切換、首次內裝、首次到新區域。桌面 390×844 相容設定不是手機硬體模擬。
4. 用逐項開關的消融比較確認各保留方案收益；量測峰值 JS heap、GPU 資源、下載 bytes 及長幀，而不是由啟動秒數推算 RAM、電量或整體 FPS。
5. 若再次嘗試預算資料或 Worker，先證明端到端成本值得，再增加架構複雜度；保留失敗回退、取消釋放，以及坡度／碰撞／步道的精確驗證。
6. 合併前重跑自動測試、正式建置、三種移動模式與品質切換；保留首次慢樣本。高品質依然可以背景準備並快取，效能模式優先省略非必要細節。

本文件只記錄既有實驗與後續建議，沒有批准自動合併或部署；本輪維持 main 與 Firebase 不變。
